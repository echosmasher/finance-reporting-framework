## Notes for Phase 3 (dashboard)

- **`brand.md` needed a machine-readable block, same problem class as tasks 6/7/8's config gaps.** Task 2's `brand.md` was pure prose + markdown tables (right for a human reading it during `/setup`, unparseable reliably by a script). Added a fenced ` ```yaml ` block at the top with the same tokens (`colors`, `status_colors`, `typography`, `logo`) — the tables/prose stay as the human-readable version, kept in sync by hand; `config_loader.load_brand()` reads only the fenced block, and raises `ConfigError` (not a silent wrong-color render) if a company's `brand.md` doesn't have one. `render_dashboard.py`'s `DEFAULT_BRAND` constant is the fallback for a company with no `brand.md` tokens at all (PLAN §7.2 "clean default theme as fallback") — it happens to reuse Example Hotels' actual color values (a reasonable neutral default, not a bug), so the fallback test used the font-family instead (`system-ui` vs the demo's configured `Inter`) to prove the fallback path genuinely triggered rather than silently loading the real config by an accident of matching values.
- **`config_loader.py` is now imported across skill boundaries.** `render_dashboard.py` lives under `skills/dashboard/scripts/` but needs `load_brand()`/`ConfigError` from `skills/analysis/scripts/config_loader.py` — rather than duplicating loader logic, it inserts `../../analysis/scripts` onto `sys.path` at import time (same pattern `tests/conftest.py` already uses). `config_loader.py`'s docstring now says it's shared, not analysis-only.
- **Avoided CSS `color-mix()`.** First draft of `dashboard_base.html` used `background: color-mix(in srgb, var(--status-note) 14%, var(--surface))` for status-pill/focus-metric tints — cut it because `color-mix()` is recent enough (Chrome 111+/Safari 16.2+/Firefox 113+) that some print/PDF engines and older browsers might not support it, and PLAN §7.4 tier 1 (file-based, shared drive, email attachment) means these have to render correctly in whatever's opened them, not just a modern browser someone controls. Tints are precomputed in Python instead (`render_dashboard.py`'s `tint()`: linear RGB blend against the surface color at a fixed 14% opacity) and passed as plain hex/`rgb()` CSS custom properties — no runtime color math in the browser at all.
- **"Audience's focus categories visually emphasized" (PLAN §7.1 item 4)** is interpreted as the P&L rows matching `pnl-structure.yaml` → `terminology.focus_metric`/`secondary_metric` (`gop`/`ebitda` for Example Hotels) — both already structured, machine-readable data the analysis JSON carries. `company-profile.md`'s prose mention of personnel costs as "a standing area of interest" is *not* wired into this emphasis mechanically — it's prose meant for the narrative pass to weigh in judgment, not a second structured emphasis list, and adding one wasn't asked for by PLAN's fairly soft wording here. Only `load_brand(config_dir)` touches `config/` directly, for the one thing the JSON never carries (brand is a dashboard-only concern). Same inputs as `render_analysis.py` (task 9) — this is a second *presentation* of the same numbers, never a second source of them.

## Notes for Phase 4 (setup)

- Task 14 (`skills/setup/SKILL.md`) leans heavily on pointing at real, already-built artifacts instead of re-deriving schema documentation in prose: `skills/setup/templates/` (task 15, not yet built) for skeleton starting files, `examples/example-hotels/config/` for a fully-worked reference example of every schema, and specific `tasks.md` notes (tasks 6/7) for *why* certain fields exist (`presentation_order`, `applies_to_brands`, the `floor ≈ Budget × pct × 1.3` threshold-sizing approach, KPI formula variable-naming). This keeps SKILL.md from drifting out of sync with the real schemas — there's one source of truth (the demo config + the engine code that reads it), not a second hand-written description of the same shapes that could quietly go stale.
- **A fourth instance of the hardcoded-config-value bug class, this one bigger than the first three (tasks 7/8/Phase-4-prep) and only partially fixed.** While writing Phase D/G's guidance, noticed `validate_data.py` hardcoded `REQUIRED_FILE_TYPES = ["actuals", "budget", "stats"]` — every company was forced to supply a "stats" file, and `preprocess.py`'s `compute_kpis()` hardcoded the exact hotel-shaped column names it expects inside that file (`rooms_available`, `rooms_sold_actual`/`budget`, `fte_actual`/`budget`). A company whose KPIs are all pure P&L ratios (GOP % alone, say) would have been forced to fabricate rooms/FTE data it doesn't have, or `/setup` would need to lie about having a stats file at all.
  - **Fixed the forced-requirement part**: `stats` moved from `REQUIRED_FILE_TYPES` to `OPTIONAL_FILE_TYPES` in `validate_data.py`; `preprocess.py`'s `preprocess_period()` now treats a missing stats file as `stats_row = {}` rather than raising `FileNotFoundError`; `compute_kpis()` only adds a stats-derived variable (`rooms_sold`, `rooms_available`, `fte`) to its evaluation namespace when the corresponding stats column is actually present, and wraps each KPI's formula evaluation in `try/except KeyError: continue` so a KPI needing a missing field is silently omitted rather than crashing the whole analysis run; `analyze.py`'s `build_kpi_entries()` skips any KPI id not present in the result. Verified directly: ran the full `/analysis` pipeline against a copy of Oslo's Feb data with the stats file deleted — GOP % (pure P&L ratio) still computed and flagged correctly, the other three KPIs (all stats-dependent) were cleanly absent from the JSON, zero crashes, all 44 tests still pass.
  - **Deliberately did NOT fix the deeper part**: the stats file's *column names* (`rooms_available`, `fte_actual`, etc.) are still hardcoded in the engine, not derived from config. Fully generalizing this — letting a company define an arbitrary operational-data file shape for KPIs with a genuinely different unit (e.g. "units produced" for a manufacturer) — would need `kpi-definitions.yaml` or `data-dictionary.md` to declare the stats schema and `preprocess.py` to build its evaluation namespace generically from whatever's declared, a meaningfully bigger refactor than the other three hardcoding fixes. Given PLAN's demo, elevator pitch, and every worked KPI example are all hotel-shaped throughout, and the ROADMAP doesn't call out cross-industry operational-data genericity as in-scope for v1, treating this as a **disclosed v1 limitation** (documented in `data-dictionary.md` §4 and `SKILL.md` Phase G, both honest about the boundary and pointing at the pure-P&L-ratio-KPI fallback that avoids it entirely) is the proportionate call here, not a silent gap. Worth a full pass if this framework is ever extended past hospitality.
  - **Pattern worth remembering across all four instances**: three were caught by something concrete breaking or looking wrong (a fixture test failing, absolute thresholds visibly over-flagging) — this one was caught by re-reading my own `SKILL.md` prose against the actual engine code while explaining Phase D/G to a hypothetical *different* company, and noticing the explanation didn't hold up. Writing the interview instructions for a genuinely different company is a good way to surface this class of bug that fixture tests (which mostly still resemble the demo) won't.
- Task 15 (`skills/setup/templates/`): all 9 templates are genuine skeletons, not copies of Example Hotels' content stripped of company names — CSV templates (`entities.csv`, `account-mapping.csv`) are header-row-only (CSV has no comment syntax, and the rows are 100% interview-driven anyway); `entities.csv`'s header is deliberately just `entity_code,name,country,currency` — the four columns the engine actually assumes exist — not the demo's `brand,size,segment_notes`, since Phase A treats those as free-form per PLAN §5.1 ("whatever they use"). YAML/Markdown templates carry inline comments explaining each field plus `REPLACE_ME`/`REPLACE_WITH_*` placeholders marking exactly what the interview fills in, and cross-reference the relevant `tasks.md` notes (task 6 for `presentation_order`/KPI formula naming, task 7 for threshold sizing) rather than re-explaining the reasoning inline. Verified all three YAML templates (`pnl-structure.yaml`, `thresholds.yaml`, `kpi-definitions.yaml`) parse cleanly with placeholder values still in them, and `brand.md`'s fenced token block loads correctly through the same `config_loader.load_brand()` path `render_dashboard.py` uses — not just eyeballed, actually round-tripped through the real loader.
- **A fifth and by far the biggest instance of the hardcoded-config-value bug class, found by PLAN's own task 16 acceptance test before even writing the test.** PLAN §11 Phase 4 explicitly requires proving `/setup`'s output works against a modified copy of the demo samples "with a different delimiter + sign convention" — reading that criterion closely (before building the test) revealed `csv.DictReader(f)` (bare, comma-only) was hardcoded in `validate_data.py`, `preprocess.py`, and `analyze.py`, and `validate_data.py`'s negative-amount check was a blanket "must be non-negative" with no sign-convention awareness at all — despite `data-dictionary.md`'s own Conventions table documenting delimiter and sign convention as if they were per-company configurable. The entire "data conventions" section of every company's `data-dictionary.md` was aspirational documentation the engine never actually read.
  - **Fixed, following the same pattern as `brand.md`**: `data-dictionary.md` gained a fenced ` ```yaml ` `conventions` block (`delimiter`, `sign_convention`, plus `decimal_separator`/`thousands_separator`/`encoding`/`date_format` for documentation — see below); `config_loader.load_data_conventions(config_dir)` reads it, filling in `DEFAULT_CONVENTIONS` for anything the block doesn't override, so a company using the defaults (comma, all-positive) doesn't need to repeat them explicitly. `validate_data.py`'s `csv.DictReader` now uses the configured delimiter, and its sign check is convention-aware via a new `amount_sign_ok()`: `all_positive` is the old blanket check; `costs_negative` expects departmental/undistributed/fixed-charge/below-EBITDA accounts negative and revenue accounts positive, checked against `pnl-structure.yaml`'s category `group` (not the account name). `preprocess.py`'s `aggregate_categories()` normalizes to costs-positive internally regardless of which convention the source used, so every `pnl-structure.yaml` subtotal formula always sees the same sign and never needs to know which convention was in play. `analyze.py`'s transaction drill-down normalizes the same way, so a "costs_negative" company's dashboard doesn't show negative line items next to a P&L table showing the same costs positive. `EXPENSE_GROUPS` (which group names are cost-like) moved into `config_loader.py` as a shared constant — it was already duplicated informally between `analyze.py`'s favorability logic and this new sign-check logic, no reason to have two copies drift.
  - **Deliberately did NOT implement configurable decimal/thousands separators** — every number must still be a plain period-decimal, no-thousands-separator string (`1234.56`) regardless of what a company's `data-dictionary.md` documents about its own convention. `full float()`-based parsing of arbitrary locale number formats (`1.234,56` vs `1,234.56`) is a real, separate piece of work PLAN's task 16 acceptance criterion doesn't actually ask for (it names delimiter and sign convention specifically, not decimal format) — disclosed plainly in `data-dictionary.md`'s Conventions section rather than silently ignored, with the honest note that this is documented-but-not-enforced.
  - Verified before moving to the actual task 16 dry run: added the same conventions block to both test fixture configs (`config/` and `config_with_ly/` — `load_data_conventions()` is now load-bearing for every config, the fixtures needed to catch up the same way they did for `brand.md`), re-ran all 44 tests (still green), and re-ran the full real-demo pipeline end to end — byte-for-byte identical output to before this fix (Oslo Feb's Utilities row: 391,068.27, INVESTIGATE, -20.38%, unchanged), confirming the default-convention path (comma, all-positive) is exactly as before for a company that never touches the new block.
- **Task 16, the actual dry run** (not committed — a verification exercise in `/tmp`, same treatment as the SKILL.md dry-runs in tasks 10/13): rather than inventing a wholly new fictional company, took the most rigorous version of PLAN's acceptance test available — the *same* underlying financial reality (Oslo's real Feb 2026 actuals/budget/stats/transactions) re-encoded into a genuinely different file format, so any divergence in output could only come from the engine handling the new convention wrong, not from different input data. Transformation: semicolon delimiter throughout, and every `departmental_expense`/`undistributed_expense`/`fixed_charge`/`below_ebitda`-group GL account's `amount` negated (revenue accounts left positive) — i.e. exactly the `costs_negative` convention this task's engine fix just added. A copied `config/` with only `data-dictionary.md`'s fenced `conventions` block edited (`delimiter: ";"`, `sign_convention: "costs_negative"`) was the only config change; zero script changes, by construction — the whole point was running the already-committed, unmodified `validate_data.py`/`preprocess.py`/`analyze.py`/`render_dashboard.py` against it.
  - **Result:** `validate_data.py` — 0 errors, 0 warnings. `analyze.py` — same 5 flags as the original run. Compared every field of all 36 P&L entries and all 4 KPIs between the semicolon/negative-cost version and the original comma/all-positive version: **zero mismatches** — identical `act`, `budget`, and `status` on every single line, not just the totals. Drill-down data (`transaction_count`, `by_vendor` breakdown) and `revenue_mix` also compared exactly equal. `render_dashboard.py` rendered a complete dashboard from the transformed data's analysis JSON with no errors. This is about as rigorous a proof of PLAN's task 16 acceptance criterion as is achievable without a live second human interview — genuinely different file encoding, byte-for-byte identical financial output, no engine code touched to make it work (all engine changes happened *before* this test, motivated by reading the acceptance criterion itself — see the "Fix: make delimiter and sign convention genuinely configurable" commit above).

- Task 7 (`analyze.py`) surfaced a real calibration bug that required going back into tasks 2-4's already-committed files — worth understanding if the flag counts ever look wrong again:
