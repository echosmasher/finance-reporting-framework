## Notes for picking this up in a new session

- `PLAN.md` is the contract. Anything marked **DECISION** there must not be deviated from without asking first.
- Two non-negotiables to re-read before every task: engine vs. config separation (nothing company-specific in `skills/` or `scripts/` — it belongs in `config/`) and Python computes / Claude interprets (all numbers deterministic and testable; Claude only narrates).
- Clean-room rule: no real company names, benchmarks, account codes, thresholds, or property codes from any prior employer, anywhere. Task 25 greps for this, but it's cheaper to never write it.
- Everything in PLAN §10 (ROADMAP) is out of scope for v1 — including partially. Resist YTD views, consolidation, and multi-currency roll-ups even when the data makes them look easy.
- Demo entity codes are plain numerics (`001`–`004`); currency follows the entity's country via the demo config's country → currency map, not a hardcoded table.
- Task 1 gotcha: the working-directory `.gitignore` rules (`inbox/*`, `outputs/*`, `config/*`, `references/*`) must stay **root-anchored** (`/inbox/*`, not `inbox/*`) — unanchored, they also match `examples/example-hotels/{inbox,outputs}`, whose contents are the committed demo data and must never be ignored.
- Task 2 decisions (all recorded in the config files themselves, summarized here for quick reference):
  - P&L structure: 27 leaf categories over 5 groups (revenue, departmental expense, undistributed expense, fixed charge, below-EBITDA), USALI-inspired. Cascade: Total Revenue → Departmental Profit → **GOP** (focus metric) → EBITDA (secondary) → EBIT → Pre-tax Income. `pnl-structure.yaml` `subtotals[].formula` is the authoritative cascade — `preprocess.py` must recompute from it, never trust source-file subtotal rows.
  - Comparison basis is **Budget only** — no rolling forecast, no Last Year data in this demo (both are optional per the engine's graceful-degradation rule). Keep `generate_demo_data.py` (task 3) to actuals + budget + transactions + stats; no LY file.
  - Added a 4th input file type beyond PLAN §4's three (actuals/budget/transactions): a **stats file** (`{ENTITY}_stats_{PERIOD}.csv` — rooms_available, rooms_sold actual/budget, FTE actual/budget) since Occupancy %, RevPAR, and Revenue per FTE all need non-P&L operational data. Documented in `data-dictionary.md`; consistent with PLAN §5.1 Phase G's "data source/format" per KPI. Task 3 must generate this file too.
  - Sign convention: **all amounts stored positive**; revenue vs. expense is inferred from the account's category group, never from a sign in the source file. Keep `generate_demo_data.py` and `validate_data.py` consistent with this — a negative value is always a data error.
  - Thresholds are **per-currency absolute** (NOK/SEK/DKK) since entities report in different local currencies with no cross-entity consolidation (PLAN §10 roadmap). Six categories get tightened bands matching `investigation-guide.md`'s six covered categories: utilities, fb_cogs, rooms_payroll, fb_payroll, property_ops_maint, admin_general.
  - `account-mapping.csv` has 125 GL accounts (not exactly ~150) across all 27 categories — a deliberate, non-padded approximation; verified every category from `pnl-structure.yaml` has ≥1 mapped account via a `uv run --with pyyaml` cross-check script (not committed).
  - Compact-brand entity (003, Stockholm) has no Spa & Wellness department — `pnl-structure.yaml` categories `spa_revenue`/`spa_payroll`/`spa_other_exp` carry `applies_to_brands: [Signature]`; task 3's generator must not produce Spa activity for entity 003, and a stray posting there is a validation *warning*, not a hard fail (see `data-dictionary.md`).
- Task 3 (`examples/example-hotels/generate_demo_data.py`, seeded RNG so output is reproducible byte-for-byte on rerun):
  - Baseline economics: room count/ADR/occupancy per entity drive `rooms_revenue`; other revenue categories are ratios of it; departmental expenses are ratios of their own department's revenue; undistributed/fixed/below-EBITDA categories are ratios of Total Revenue. All ratios are named constants at the top of the file.
  - January seasonality is baked into the baseline generator (not a task-4 story): `insurance` and `admin_general` actuals carry the annual-premium/audit-fee lump sum described in `company-profile.md`/`thresholds.yaml`, while Budget stays flat — so the deterministic engine (task 7) *will* mechanically flag both every January, and the narrative pass is the thing that's supposed to recognize them as expected via `investigation-guide.md`'s admin_general checklist and the `thresholds.yaml` seasonality_notes. This is a live exercise of that mechanism, not a bug.
  - Realism gotcha caught during generation: initially keyed the "vendor invoice vs. internal payroll" transaction split off *category* (only `rooms_payroll`/`fb_payroll`/`spa_payroll`), which put nonsense rows like a law firm "invoicing" the `admin_general` account "Finance & Accounting Salaries". Fixed by also checking the individual GL account name for `"Salaries"` (`is_payroll_account()`) — several categories (admin_general, sales_marketing, property_ops_maint) mix salary accounts with genuine vendor-invoiced accounts in `account-mapping.csv`. If more categories/accounts are added later, re-check this.
  - Transactions are generated only for expense-side accounts (revenue is PMS-posted in a real hotel, nothing to vendor-invoice) and never for `depreciation`/`interest_expense` (system journal entries, no vendor) — a deliberate scope decision, not a schema requirement (`data-dictionary.md` itself stays generic on this).
  - `STORY_OVERRIDES` (currently `{}`) is the injection point task 4 populates: `(entity_code, period, category_id) -> fn(budget_amount, actual_amount) -> new_actual_amount`, applied after baseline economics, before the GL-account split.

- Task 6 (`preprocess.py`) needed two config fixes made *before* writing it, both now live in the committed config:
  - `pnl-structure.yaml` gained a `presentation_order` list (categories and subtotals interleaved in the exact P&L row order — e.g. Total Revenue right after the last revenue category, EBIT sitting *between* Depreciation and Interest Expense rather than after both). This is literally what PLAN §5.1 Phase C asks `/setup` to elicit ("ordered hierarchy") — task 2 captured the categories/subtotals/formulas but missed capturing their presentation order as a separate explicit list. `preprocess.py` renders rows in this order; it does not try to infer one.

  - Added a `data-dictionary.md` §5 "Last Year (optional)" file type (`{ENTITY}_lastyear_{PERIOD}.csv`, same shape as Actuals) — LY is a first-class optional comparison basis per PLAN §5.1 Phase C (not on the ROADMAP's out-of-scope list), but task 2 never defined its file shape since this demo company doesn't have one. `preprocess.py` loads it conditionally on `terminology.last_year_available`; since this demo's config has that as `false`, the LY code path is implemented but not exercised by any committed fixture — worth a synthetic test case in task 8 if LY coverage matters.

  - `eval_formula()`'s tiny DSL (`sum_group(GROUP)`, `A - B`, `A / B`) is intentionally minimal — every formula in the committed config fits one of these three shapes; division by zero returns `0.0` rather than raising, so an entity with no revenue yet shows a blank ratio instead of crashing the run.
  - Verified against the demo: Oslo Feb's Utilities row reproduces the exact planted-story numbers from task 4 (Act 391,068 vs Budget 491,144); `ratios_actual["gop_pct"]` matches `kpis["gop_pct"]["actual"]` exactly (same formula, evaluated through two different code paths — good cross-check); Stockholm's three Spa categories resolve cleanly to all-zero rows with no crash (aggregate_categories defaults every category id to 0.0 up front, so `sum_group` never KeyErrors on a category with no postings).
- Task 7 (`analyze.py`) surfaced a real calibration bug that required going back into tasks 2-4's already-committed files — worth understanding if the flag counts ever look wrong again:
  - **The bug:** first run produced 12-31 flags per entity/period out of 40 possible items (27 categories + 9 subtotals + 4 KPIs) — way too many for a report meant to "lead with wins." Root cause #1: `thresholds.yaml`'s absolute floors (e.g. NOK 20,000 default, NOK 15,000 for rooms_payroll) were sized without checking them against the demo's actual dollar scale — a category running several million NOK/month breaches a 20,000 NOK floor from *any* 1% noise-driven wobble, so the NOTE-tier "breach pct OR absolute" logic was firing on totally ordinary variance via the absolute leg alone, even when pct was comfortably inside its own threshold (e.g. `total_revenue` at 0.87% deviation, under its 2% pct threshold, still flagged NOTE because its 40,000 NOK floor was trivial to clear). Root cause #2: the demo generator applied the same noise to genuinely variable categories (revenue, payroll, utilities) *and* to categories that are contractually fixed in real hotel accounting (rent, management/franchise fees, property tax, D&A, loan interest) — none of which should show meaningful month-to-month variance vs Budget in reality.
  - **The fix, three parts:** (1) recalibrated every `thresholds.yaml` absolute floor off **Budget** (not Actual — Actual is exactly what noise/stories perturb) using the formula `floor ≈ Budget × pct_threshold × 1.3`, so a category sitting *exactly* at its own pct threshold does NOT also clear the absolute floor — INVESTIGATE now means genuinely large in both relative *and* dollar terms. Where NOK is shared by two differently-sized entities (Oslo/Bergen), floors are anchored to the *larger* one (Oslo) so the smaller safely falls back to pct-only discrimination instead of risking the same bug in reverse. Added explicit overrides for six large subtotals (`total_departmental_expenses` through `pretax_income`) that were previously falling through to the default and misfiring the same way. (2) Split `generate_demo_data.py`'s flat-ratio noise: `rent_lease`/`property_tax`/`depreciation`/`interest_expense`/`insurance` (outside January) now track their own Budget dollar amount directly with near-zero noise (`TRUE_FIXED_DOLLAR_CATEGORIES`), instead of scaling off `total_revenue_actual` and inheriting *its* noise — `management_fees`/`franchise_fees` correctly keep scaling with revenue since real contracts define them as a % of it. (3) Halved every remaining `*_NOISE_SD` constant again (occupancy 0.015→0.008, ADR 0.010→0.005, etc.) — noise compounds through 2-3 levels of the driver chain (occupancy/ADR → rooms_revenue → every category that uses it as a driver), so even "small" individual stdevs were producing large effective swings by the time they reached leaf categories, and a single unlucky upstream draw for one entity/month could bias nearly its whole P&L in the same direction at once (this is why Bergen and Stockholm's January flag counts stayed stubbornly high even after fix #1 — it wasn't January being special, just where an unlucky run of draws landed in the RNG sequence for those two entities).
  - **Regenerating broke Story 4 once:** changing noise *parameters* (not just re-running) reshuffles every downstream `rng.gauss()` draw even under the same seed, since the seed determines the underlying random state but the sd scales the output. Stockholm's "beats forecast cleanly" story was emergent (relying on noise happening to land favorably), so recalibrating noise flipped its January GOP slightly negative. Fixed by making it deliberate like the other three: `story_stockholm_efficient_overhead` trims Property Ops & Maintenance and IT & Systems to 92% of Budget every month via `STORY_ACCOUNT_SPLITS`, guaranteeing a real, reproducible GOP beat regardless of what the noise draws do elsewhere. Lesson: don't leave a *required* story to emergent randomness — plant it explicitly, the same way as the other three, from the start.
  - **End state, re-verified after all of the above:** Jan (the seasonality month) now runs 8-15 flags per entity, and for two of the four entities (Oslo, Copenhagen) the January flags are *entirely* explained by the legitimate insurance/admin_general cascade (insurance → total_fixed_charges → ebitda → ebit → pretax_income, admin_general → total_undistributed_expenses → gop) with zero residual noise flags; Feb/Mar run 0-10 flags, mostly the deliberate stories. All three README-documented story dollar figures are byte-for-byte unchanged (Budget never carries noise, and the stories are computed off Budget, so none of this touched them) — re-verified directly against `inbox/` after every regeneration. Zero negative amounts, zero transaction-reconciliation mismatches, Stockholm's Spa rows still clean zero, all reconfirmed post-fix.
  - `analyze.py` design notes: INVESTIGATE requires *both* pct and absolute breached; NOTE requires *either*; `favorable`/`unfavorable` direction is computed mechanically from each category's `group` (cost-like groups: `departmental_expense`, `undistributed_expense`, `fixed_charge`, `below_ebitda`) or, for subtotals (which don't carry a `group`), derived from the formula shape (`is_expense_like_subtotal()`: a straight `sum_group(X)` is cost-like iff `X` is a cost group; every subtraction-shaped subtotal in the cascade nets a cost off a revenue/profit figure, so its result is always profit-like — see task 8 notes below for why this replaced an earlier hardcoded id list) — deliberately *not* judgment (e.g. Oslo's Feb Utilities gap is mechanically `favorable=True`, which is numerically correct and exactly why `investigation-guide.md` exists: the narrative pass, not the engine, is responsible for recognizing "a low Utilities number is often a missing invoice, not genuine savings"). KPI thresholds use a simpler two-tier notice/investigate shape (no AND logic) since a currency absolute floor doesn't translate to a per-room or percentage-point KPI; which shape applies is derived from the KPI's `format` field (`percent` → percentage-point, `currency` → relative %), not hardcoded to any KPI's name — same reasoning as the subtotal fix. Transaction drill-downs are grouped by vendor and by account (no "type" field exists in the transactions schema, so PLAN §6 step 4's "vendor/account/type" is implemented as vendor+account only — noted as a scope decision, not an oversight). Revenue-mix shift for a category is literally the same number as its `diff_pp` in `preprocess.py`'s row output, surfaced separately under `revenue_mix` so the narrative pass doesn't have to filter the full P&L list to find just the revenue lines.
