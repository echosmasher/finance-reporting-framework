# Improvement ideas — post-v1 polish, prioritized

Recommendations from a repo review (2026-08-08), aimed at maximizing the
first-two-minutes impression for a reviewer visiting the repo — the README's
stated target audience (PLAN §1). Ordered by leverage. None of these are
committed work; see `tasks.md` Phase 6 for what actually gets built.

Context for the ordering: the repo's engineering fundamentals are already
strong (CI, live demo, planted-story verification, honest docs, the
engine/config discipline recorded in `tasks.md`). The actual gap is that the
first 30 seconds of a visit are visual, and the dashboard is currently a
(very clean) table of text with zero data visualization.

---

## 1. Charts in the dashboard — especially a GOP bridge (waterfall)

The single highest-leverage change.

- **A variance waterfall ("Budget GOP → Actual GOP bridge")** near the top:
  budget GOP on the left, actual on the right, flagged categories as the
  bridging bars. This is *the* artifact controllers and CFOs actually use —
  it demonstrates domain fluency, not just coding — and it makes the Oslo
  Utilities story visible at a glance instead of buried in row 21 of the
  P&L table.
- **Sparklines** on KPI cards and flagged rows (needs the trend data from
  idea 3).

Implementation constraint that makes this cheap: inline SVG generated by
Python in `render_dashboard.py` keeps the zero-external-requests principle
fully intact (PLAN §7.2) — no chart library, and consistent with
"Python computes." Also upgrades the README screenshots for free.

## 2. A portfolio overview page (all four entities at a glance)

4 entities × 3 months of output are committed, but a visitor has to open 12
separate files. One `Portfolio-Overview_{PERIOD}.html` — a card per entity
with KPIs, GOP vs budget, flag counts, linking into each dashboard — becomes
the new hero screenshot.

Crucially, this **dodges the hard roadmap items**: it is not consolidation
(no summing across NOK/SEK/DKK, no eliminations) — just a side-by-side.
"Group controller sees all properties on one screen" is exactly the view a
domain reviewer will imagine wanting.

## 3. A trend view — the data already exists

Three months are committed but every output is single-month. A small
multi-period strip (KPI sparklines, GOP by month, flag history per category)
makes the Oslo story *land*: Utilities dips in Feb, catches up in Mar —
visible as a shape, provable as "the framework predicted the reversal and it
happened." A single-month dashboard cannot deliver that moment.

The v1 roadmap freeze (PLAN §10) was explicitly v1-only; Phase 6 is open, so
this is fair game — same graduation path `/feedback` took.

## 4. An animated GIF or 60-second demo at the top of the README

The strongest thing about the project is the *loop* — drop files, run
`/analysis`, watch it flag the missing invoice, read the narrative.
Screenshots can't show a loop. A short GIF (terminal running `/analysis` →
flags appearing → dashboard opening) above the screenshot table is cheap to
produce and dramatically raises the "I get it in 10 seconds" factor. Most
reviewers never clone the repo; the README *is* the demo for them.

## 5. Turn the GitHub Pages index into a guided tour

The live demo link is where visitors actually click, and it currently lands
on a file listing. Restructure it as a story: *"February: Utilities came in
20% under budget. Looks like a win. Here's the framework explaining why it
isn't →"* — with the three planted stories as the navigation. The narrative
already exists in `examples/example-hotels/README.md`; it just needs to be
the front door instead of buried in a subdirectory.

## 6. Differentiator: a visible audit trail on flagged rows

The core thesis is "auditable AI — no LLM ever produces a number." Make that
*inspectable in the artifact itself*: a small "why was this flagged?"
expander on each flagged row showing the threshold rule from
`thresholds.yaml`, the computed variance, and which config line produced the
flag. For a finance audience — and for anyone probing "how do you keep LLMs
honest?" — seeing the provenance chain in the dashboard is more convincing
than reading about it in the README.

---

## Deliberately not worth the time (for this goal)

The inbox watcher, localization packs, multi-currency consolidation, and GM
write-back are all real `ROADMAP.md` items, but none of them show up in a
two-minute review — and the ROADMAP entries documenting *why* they're
deferred already earn the credit for having thought about them.

## Suggested build order

Idea 1 first: the waterfall + inline-SVG charting in `render_dashboard.py`
upgrades everything downstream — screenshots, the live demo, and the
portfolio page (idea 2) would all reuse the same chart code. Then 2 → 3
(shared trend data), with 4 and 5 as independent, cheap follow-ups.
